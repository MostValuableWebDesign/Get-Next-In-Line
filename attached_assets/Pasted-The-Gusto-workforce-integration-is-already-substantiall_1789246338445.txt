## 1. Fix capability ownership initialization

Current problem:

The sync services correctly require Gusto to be the primary owner of capabilities such as:

* employees
* payroll
* compensation

However, after a successful real Gusto OAuth connection there may be no persisted `tenant_integration_capabilities` rows, causing valid sync requests to fail with:

```text
gusto is not the primary owner of employees
```

or equivalent 409 errors.

Implement a production-safe capability assignment flow.

### Required behavior

After a successful Gusto OAuth connection and successful token introspection, determine the capabilities GNIL can actually use from the granted scopes.

Use the currently verified mappings:

```text
employees:read
    -> employees

payrolls:read
    -> payroll

compensations:read + employees:read
    -> compensation
```

Only create assignments for capabilities that:

1. GNIL actually implements for Gusto
2. the authenticated Gusto connection has the required granted scopes for

Persist them as primary assignments in `tenant_integration_capabilities`.

### Important conflict rule

DO NOT silently steal a capability from another provider.

For each capability:

* If no primary provider exists:
  assign Gusto as primary.

* If Gusto is already primary:
  leave it unchanged.

* If another provider is already primary:
  DO NOT replace it automatically.
  Preserve the existing provider.
  Surface that capability as needing explicit owner/admin reassignment if necessary.

The operation must be idempotent.

Repeated OAuth/reconnect must not create duplicate assignments.

### Scope downgrade/reconnect behavior

If a reconnect grants fewer scopes than before:

* do not claim the capability is healthy
* existing assignment may remain persisted for administrative history
* Operations overview should surface `missing_scope`
* sync must remain blocked until the required scope is restored or another provider becomes primary

Do not silently delete configuration simply because a scope disappeared.

  "compensation",
  "onboarding"

Change the Gusto provider definition so it advertises only functionality GNIL currently implements.

For now this should be:

```ts
capabilities: [

  "compensation"
]
```

Do not advertise:

* onboarding
* contractors
* benefits
* tax_documents
* time_tracking
* time_off

unless the current code contains a real, verified implementation for the capability.

Keep the general capability taxonomy so future providers can support these later.

## 7. Keep capability ownership provider-agnostic

Do not hard-code capability assignment logic deep inside UI components.

Prefer a service/helper such as:

```ts
reconcileProviderCapabilityAssignments({
  tenantId,
  providerId,
  grantedScopes
})
```

It should use the provider registry definition:

```ts
definition.capabilities
definition.requiredScopes
```

rather than duplicating Gusto-specific scope logic everywhere.

This allows future providers like Homebase, ADP, Square, or Rippling to use the same mechanism.

A Gusto-specific OAuth service can invoke this generic service after successful authorization.
