## 1. Handle capability reconciliation failure after successful OAuth

Current flow:

```text
Gusto OAuth succeeds
→ credentials/token state are persisted as connected
→ capability reconciliation runs afterward
```

Problem:

If capability reconciliation fails after the OAuth transaction has already persisted the connection as `connected`, GNIL can end up in a partial state:

```text
Gusto = connected
but
required capability assignments were not created
```

Then sync actions may fail with ownership-related 409 responses.

Fix this without rewriting the OAuth flow.

### Required behavior

After successful OAuth and token introspection:

1. Persist the verified Gusto connection as currently implemented.
2. Run `reconcileProviderCapabilityAssignments`.
3. If reconciliation succeeds:

   * leave connection healthy/connected
   * clear any capability-setup-related error
4. If reconciliation fails:

   * DO NOT delete the valid OAuth credentials
   * DO NOT mark the OAuth token invalid
   * change the workforce integration state to `degraded`
   * set a safe `lastError`, for example:

```text
Capability configuration failed. Retry integration setup.
```

* log an integration event such as:

```text
capability_reconciliation_failed
```

* do not expose raw database/provider errors or secrets to the frontend

The valid Gusto connection should remain recoverable without requiring a new OAuth flow unless credentials themselves are invalid.

### Retry behavior

Add a reusable service operation so capability reconciliation can be retried independently from OAuth.

For example:

```ts
reconcileConnectedProviderCapabilities({
  tenantId,
  providerId
})
```

It should:

* load the existing connected provider
* use its persisted granted scopes
* call the existing provider-neutral capability reconciliation service
* restore connection status from `degraded` to `connected` if reconciliation succeeds and no other degraded condition remains

Do not duplicate capability mapping logic.

### Testing

Add tests for:

#### Successful OAuth + successful reconciliation

```text
OAuth succeeds
capability reconciliation succeeds
connection = connected
expected assignments exist
```

#### Successful OAuth + failed reconciliation

Simulate a reconciliation/database failure.

Expected:

```text
credentials remain persisted
providerAccountId remains persisted
connection = degraded
lastError indicates capability configuration problem
```

The connection must NOT incorrectly remain healthy `connected`.

#### Retry succeeds

After the failed reconciliation:

```text
retry reconciliation
→ assignments created
→ connection returns to connected
```

if no other failure exists.

## 2. Make Gusto Manage actions capability-aware

Current Gusto Manage menu shows:

```text
Sync staff
Sync payroll
Sync compensation
```

whenever the Gusto provider is active.

Problem:

This ignores the actual capability ownership and state.

For example:

```text
employees    → Gusto
payroll      → ADP
compensation → Gusto
```

The UI still shows `Sync payroll`, even though the backend will correctly reject it.

Or:

```text
compensation → Gusto
state = missing_scope
```

The UI still allows an action that cannot succeed.

Fix the frontend using the existing Operations overview data.

DO NOT weaken backend protection.

### Required UI logic

Use:

```ts
data.capabilityAssignments
```

to determine whether each action is available.

For each action:

### Sync staff

Enabled only when:

```text
capability = employees
providerId = gusto
state = connected
```

### Sync payroll

Enabled only when:

```text
capability = payroll
providerId = gusto
state = connected
```

### Sync compensation

Enabled only when:

```text
capability = compensation
providerId = gusto
state = connected
```

### Behavior for unavailable actions

Prefer either:

* hide actions Gusto does not own, or
* show them disabled with a useful reason

Use disabled states if they improve discoverability.

Examples:

```text
Sync payroll
Disabled — Managed by another provider
```

```text
Sync compensation
Disabled — Additional Gusto permission required
```

```text
Sync staff
Disabled — Capability setup required
```

Do not allow users to click an action that is already known to fail.

## 3. Keep provider status separate from capability state

Do not assume:

```text
Gusto connected
=
all Gusto capabilities available
```

A provider can be connected while individual capabilities are:

```text
connected
missing_scope
failed
unavailable
owned by another provider
```

Keep this distinction intact.

The provider card can remain `Connected` while specific sync actions are unavailable.
