The Gusto integration is already implemented and should NOT be broadly refactored.

DO NOT redesign Operations.
DO NOT change OAuth architecture.
DO NOT change workforce/payroll/compensation synchronization logic.
DO NOT touch unrelated modules.

This task is narrowly focused on exposing the existing capability-reconciliation recovery flow to an admin.

## Goal

The backend already has:

```ts id="xy1jgv"
reconcileConnectedProviderCapabilities({
  tenantId,
  providerId
})
```

This correctly repairs a Gusto connection when OAuth succeeded but post-OAuth capability reconciliation failed.

Currently, however, there is no production API/UI workflow for an admin to trigger that retry.

Implement a safe `Retry Setup` flow.

---

## 1. Add an admin-only retry endpoint

Add an endpoint following the existing Operations route conventions.

Recommended:

```text id="p9ad3h"
POST /operations/integrations/gusto/reconcile
```

Requirements:

* integration-admin roles only
* require a valid selected tenant/business
* provider must already have persisted Gusto credentials
* provider must be `connected` or `degraded`
* call:

```ts id="aruy6p"
reconcileConnectedProviderCapabilities({
  tenantId,
  providerId: "gusto"
})
```

* do NOT perform a new OAuth flow
* do NOT request new Gusto credentials
* do NOT bypass capability scope rules

Return a safe response such as:

```json id="3fmi4k"
{
  "status": "connected",
  "assigned": [],
  "alreadyOwned": [],
  "conflicts": [],
  "unavailable": []
}
```

Use the actual reconciliation result structure already present in the codebase.

Do not return credentials, provider raw responses, or internal database errors.

---

## 2. Show Retry Setup only for the correct degraded condition

In the Gusto Manage UI, detect when:

```text id="2tfmzq"
provider.status = degraded
AND
provider.lastError = "Capability configuration failed. Retry integration setup."
```

For only that condition, display:

```text id="859urh"
Retry Setup
```

The action should call the new reconciliation endpoint.

Do not show Retry Setup for unrelated degraded states.

Examples where Retry Setup should NOT appear:

* payroll sync failure
* compensation sync failure
* provider outage
* token refresh failure
* reauthorization_required

Those should retain their existing handling.

---

## 3. Retry Setup UX

When clicked:

```text id="2b67lc"
Retry Setup
→ mutation starts
→ disable action while pending
```

On success:

* invalidate Operations overview query
* refresh provider/capability state
* clear displayed capability-setup error
* provider should show Connected if reconciliation successfully repaired the specific degraded state

On failure:

* keep provider degraded
* show a safe user-facing message such as:

```text id="5lrj07"
Unable to complete Gusto setup. Please try again.
```

Do not display raw DB/provider errors.

---

## 4. Improve OAuth callback result slightly

Current behavior can redirect to:

```text id="60j2f6"
/operations/integrations?gusto=connected
```

even if OAuth succeeded but capability reconciliation caused the connection to become degraded.

Improve the callback result so the redirect reflects the actual setup outcome.

Preferred behavior:

### OAuth + reconciliation succeed

```text id="yj2h0r"
/operations/integrations?gusto=connected
```

### OAuth succeeds but capability setup fails

```text id="gsanwo"
/operations/integrations?gusto=setup_required
```

### OAuth/token exchange itself fails

Keep the existing error behavior.

Do NOT treat a capability-reconciliation failure as OAuth credential failure.

If changing the return type of `completeGustoConnection` is useful, use something clear such as:

```ts id="vqaocn"
{
  tenantId,
  status: "connected" | "setup_required"
}
```

or equivalent.

Keep credentials preserved in the `setup_required` case.

Normal successful flow must remain:
